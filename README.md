# d0c_sight

인프라 에러 메시지를 입력하면 **원인 후보와 대응 절차를 근거와 함께** 제시하는 시스템.

> **핵심 원칙: 근거 없는 답변은 내지 않는다.**
> 답변의 각 주장이 어느 문서 어느 절에서 왔는지 추적할 수 있어야 한다.
> 틀렸을 때 원인이 데이터인지 검색인지 모델인지 구별할 수 있어야 한다.

---

## 동기

인프라 운영 중 처음 보는 에러가 나면 지금은 이렇게 한다.

```
에러 메시지 검색 → 공식 문서·GitHub 이슈·스택오버플로 열 몇 개 열람
→ 우리 상황과 유사한 사례 발견 → 대응
```

30분에서 몇 시간이 걸린다.

## 문제

일반 검색이나 범용 LLM으로 대체되지 않는 이유가 있다.

- **버전이 답을 바꾼다.** PostgreSQL 14와 18의 답이 다른데 검색 결과는 버전을 구분해주지 않는다
- **근거를 확인할 수 없다.** LLM이 그럴듯한 설정값을 말해도 그것이 어느 문서에서 왔는지 알 수 없다
- **운영 중에는 확인 비용이 크다.** 틀린 조치의 대가가 크므로 출처 없는 답은 쓸 수 없다

## 방법

```
문서 수집 → 구조 보존 청킹 → 하이브리드 검색 → 근거 추적 → 에이전트 루프
```

| 결정 | 내용 | 근거 |
|---|---|---|
| 1차 도메인 | PostgreSQL 18 (인덱싱 기준 18.6) | [ADR 0001](docs/decisions/0001-scope-and-domain.md) |
| 수집 | 공식 릴리스의 사전 빌드 HTML tarball | [ADR 0001](docs/decisions/0001-scope-and-domain.md) |
| 소스 추상화 | 인터페이스는 지금, 구현체는 하나 | [ADR 0002](docs/decisions/0002-source-abstraction.md) |

구조 보존 청킹이 이 프로젝트의 첫 난제다. 문자 수로 자르면 SQLSTATE 코드와 조건명이
분리되어 양쪽 다 의미를 잃는다. 그래서 **구조가 원자 단위를 정하게** 했다 — 정의목록
항목은 그대로, 표는 헤더를 반복하며 행 그룹으로, 코드는 자르지 않고, 산문만 모은다
([ADR 0003](docs/decisions/0003-chunking-strategy.md)).

전략을 세우기 전에 문서 1,148개를 전부 실측했고, 그 결과가 사전 가정 하나를 뒤집었다.
설정 파라미터는 표가 아니라 정의 목록이었다 — `<dt>` 12,992개 대 표 486개.

| Phase 1 산출 | |
|---|---|
| 문서 → 청크 | 1,131 → 16,442 (인덱싱 제외 7) |
| 섹션 앵커 커버리지 | 4,023 / 4,023 (100%) |
| 분할된 청크 | 352 (2.1%) |
| 처리 시간 | 1.7초 |

## 개발

```bash
uv run d0c-sight ingest        # 문서 수집 → 청크 JSONL
```

```bash
uv sync                # 의존성 설치
uv run pytest          # 테스트
uv run ruff check .    # 린트
uv run ruff format .   # 포맷
uv run mypy            # 타입 검사
pre-commit install     # 훅 설치 (최초 1회)
```

`data/` 는 버전 관리하지 않는다. 수집물은 전부 재현 가능해야 한다.
