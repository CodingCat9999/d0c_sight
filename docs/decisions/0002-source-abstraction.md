# 0002. 소스 추상화 — 인터페이스는 지금, 구현체는 하나

- 상태: 채택됨
- 날짜: 2026-09-10

## 배경

이 시스템은 결국 여러 문서 소스를 다룬다(ADR 0001 의 확장 계획). 소스마다 수집 방식과
형식이 다르지만, 상위 계층(청킹·검색·근거 추적)은 소스가 무엇인지 몰라야 한다.

문제는 **언제 추상화하느냐**다. 소스가 하나뿐인데 일반화 기계부터 만들면 그것은 실제
사례가 아니라 상상에서 나온 추상화이고, 두 번째 사례를 만나면 어차피 틀린다. 반대로
추상화를 전혀 두지 않으면 두 번째 소스를 넣을 때 상위 계층 전체를 고쳐야 한다.

## 결정

**인터페이스는 지금 잡되, 구현체는 하나만 만든다.**

- `sources/protocol.py` 에 `Source` 프로토콜을 정의한다 — 수집 / 파싱 / 메타데이터
- 구현체는 `sources/postgres_docs/` 하나뿐이다
- **두 번째 소스가 생길 때 인터페이스를 고친다.** 그때가 인터페이스가 옳은지 처음으로
  검증되는 시점이다

계층 의존 방향을 단방향으로 고정한다.

```
domain  ←  sources  ←  pipeline  ←  cli
```

`domain` 은 프로젝트 내부의 어떤 모듈도 import 하지 않는다. 이 규칙은 사람의 주의력이
아니라 `tests/guards/test_layering.py` 가 AST 로 강제한다.

**버전 메타데이터 필드는 지금 넣는다.** 1차에서는 한 버전만 다루지만, 나중에 추가하면
전체 재인덱싱이 필요하다. major(`18`)와 full(`18.6`)을 분리한다 — 질문은 major 단위로
들어오고 재현성은 full 단위로 걸리기 때문이다.

## 대안

### `Source` 프로토콜을 `domain/` 에 둔다

기각. 프로토콜은 "외부 문서를 도메인 모델로 옮기는 방법"에 대한 계약이지 도메인 개념이
아니다. `domain` 에 두면 도메인이 수집이라는 관심사를 알게 되고, "`domain` 은 아무것도
import 하지 않는다"는 규칙이 설득력을 잃는다. `pipeline` 은 `Source` 프로토콜에만
의존하고 `postgres_docs` 를 모르므로 목적은 이미 달성된다.

### 추상화 없이 시작하고 두 번째 소스에서 도입한다

기각. 상위 계층이 PostgreSQL 문서 구조에 직접 의존하게 되고, 그 의존은 코드 곳곳에
퍼져 나중에 걷어내기 어렵다. 프로토콜 하나를 두는 비용은 파일 하나이고, 그것이 상위
계층의 언어를 도메인 모델로 강제하는 효과가 있다.

### 처음부터 여러 소스를 지원한다

기각. ADR 0001 의 "한 번에 한 소스" 원칙과 충돌한다. 무엇 때문에 문제가 생겼는지
구별할 수 없게 된다.

### 계층 규칙을 문서로만 남긴다

기각. 문서로만 있는 규칙은 지켜지지 않는다. 특히 급할 때 깨진다. AST 검사 테스트로
강제하고, 그 검사기 자체에 짝 테스트를 붙여 검사기가 빈 집합을 반환하는 경우까지 막는다.

## 결과

### 얻는 것

- 상위 계층이 소스 구현을 모른다. 두 번째 소스 도입 시 고칠 범위가 좁다
- 계층 규칙이 사람 주의력이 아니라 테스트로 강제된다
- 나중에 넣으면 재인덱싱이 필요한 버전 필드를 미리 확보한다

### 감수하는 것

- **프로토콜이 지금은 검증되지 않은 상태다.** 구현체가 하나뿐이라 인터페이스가 옳은지
  알 수 없다. 이것은 의도된 것이며, 두 번째 소스에서 고칠 것을 전제한다.
  **인터페이스가 맞다고 가정하고 그 위에 여러 계층을 쌓지 않는다**
- 파일과 간접 계층이 하나 늘어난다

### 언제 재검토하는가

- **두 번째 소스(메일링 리스트/이슈)를 넣을 때.** 이때 프로토콜을 고치는 것이 정상이며,
  고칠 필요가 없었다면 그것은 운이 좋았던 것이지 설계가 옳았던 증거가 아니다
- 계층 가드가 정당한 코드를 반복해서 막을 때 — 계층 구분 자체를 재검토한다
