# 0003. 청킹 전략 — 구조가 원자 단위를 정한다

- 상태: 채택됨
- 날짜: 2026-09-10

## 배경

청킹은 이 프로젝트의 첫 난제다. 문자 수로 자르면 표의 코드와 조건명이 분리되어 양쪽 다
의미를 잃고, 코드 블록이 중간에서 끊기면 실행할 수 없는 조각이 남는다.

전략을 정하기 전에 **PostgreSQL 18.6 문서 1,148개 전부를 실측했다.** 그 결과가 사전
가정 하나를 뒤집었다.

### 실측 결과

| 항목 | 값 |
|---|---|
| 문서 수 | 1,148 |
| 섹션 `<div>` 앵커 커버리지 | 3,617 / 3,617 (**100%**) |
| `<dt>` (정의목록 항목) | **12,992** |
| 콘텐츠 표 | 481 |
| 중첩 표 | **0** |
| 코드 블록 보유 문서 | 683 (59.5%) |
| 표 보유 문서 | 282 (24.6%) |
| 순수 산문 문서 | 277 (24.1%) |
| 파일 크기 | 2 KB ~ 518 KB (**250배 편차**) |

**설정 파라미터는 표가 아니었다.** 사전에는 "설정 표"가 주요 난제라고 보았으나 실물은
`<dl class="variablelist">` 정의 목록이다.

```
runtime-config-connection.html :  49,885 B   표 0개   <dt> 46개
runtime-config-resource.html   :  65,657 B   표 0개   <dt> 50개
```

정의목록 항목(`<dt>`+`<dd>`) 5,135개의 본문 문자수:

| min | median | p75 | p90 | p99 | max |
|---|---|---|---|---|---|
| 6 | **179** | 399 | 774 | 3,066 | 63,688 |

2,000자를 넘는 항목은 108개(2.1%)뿐이다. **대부분이 청크 하나에 그대로 들어간다.**

콘텐츠 표 481개의 바이트 크기:

| median | p75 | p90 | p99 | max |
|---|---|---|---|---|
| 2,521 | 4,946 | 10,927 | 35,376 | **103,355** |

8 KB 초과는 74개(15.4%)다. **표는 대부분 작고, 소수의 거대 표만 문제다.**

## 결정

### 1. 원자 단위는 문서 구조가 정한다

| 구조 | 원자 단위 | 근거 |
|---|---|---|
| `<dl class="variablelist">` | `<dt>`+`<dd>` 쌍 하나 | median 179자, p90 774자 — 대부분 그대로 들어간다 |
| `<table class="table\|informaltable">` | 표 전체 (임계값 이하일 때) | 헤더와 행이 분리되면 양쪽 다 무의미해진다 |
| `<pre class="programlisting\|synopsis\|screen">` | 블록 전체 | **절대 중간에서 자르지 않는다** |
| 그 외 산문 | 섹션 내 누적 | |

`<pre>` 의 class 를 보존한다. `programlisting`(예제 코드) 2,629개,
`synopsis`(명령 문법) 876개, `screen`(실행 출력) 613개는 의미가 다르다. 검색에서
"문법이 뭐냐"와 "출력이 어떻게 생겼냐"는 다른 질문이다.

### 2. 임계값

각 임계값은 한 문장으로 말할 수 있는 뜻을 가진다(BRIEF §6.5). 셋 다 실측 분포에서
**일부만 걸리도록** 잡았다 — 전부 걸리면 잡음이고, 하나도 안 걸리면 검증된 적 없는
코드다.

| 임계값 | 값 | 뜻 |
|---|---|---|
| `TARGET_CHARS` | 1,200 | 정의목록 항목 p90(774자)을 하나로 담고도 여유가 있는 크기 |
| `MAX_CHARS` | 2,400 | 이보다 큰 정의목록 항목은 1.0% 뿐이다 — 분할이 예외임을 뜻한다 |
| `TABLE_MAX_BYTES` | 4,096 | 표 486개 중 9.3%(45개)만 행 분할 대상이 된다 |

**임계값을 청크 메타데이터에 실어 보낸다.** 나중에 값을 바꿔도 과거 결과와 비교할 수
있어야 한다.

### 3. 거대 표는 헤더를 반복하며 행 그룹으로 나눈다

`TABLE_MAX_BYTES` 를 넘는 표는 헤더 행과 구분선을 각 조각에 **반복 포함**하고 나머지
행을 그룹으로 나눈다. 최악 케이스인 `sql-keywords-appendix.html` 의 846행 표는 12조각이
된다. 헤더 없는 행 조각은 만들지 않는다.

> **정정 (구현 후).** 이 임계값을 처음에 8,192 로 잡으며 "표 481개 중 상위 15%(74개)"를
> 근거로 들었으나, 그 수치는 **원본 HTML 바이트** 기준이었다. 실제 적용 대상은 태그가
> 제거된 마크다운 직렬화 결과이고, 그 기준으로는 8,192 에 2.7%(13개)만 걸린다.
> 거의 걸리지 않는 임계값은 검증된 적 없는 코드다(BRIEF §6.5). 4,096 으로 낮추니
> 9.3%(45개)가 걸려 원래 의도에 맞고 `MAX_CHARS`(2,400)와의 간극도 줄어든다.
> **같은 이름의 수치라도 무엇을 재고 있는지가 다르면 다른 값이다.**

### 4. 근거 링크 단위는 섹션 앵커다

섹션 `<div>` 3,617개 전부에 `id` 가 있다(100%). 모든 청크는 자신이 속한 섹션의 앵커를
보존하며, 이것이 `#ERRCODES-APPENDIX` 형태로 공식 문서 URL 에 붙는다. Phase 6 의 근거
추적은 이 앵커 위에 세운다.

### 5. 인덱싱에서 제외하는 것

색인·목차 성격이라 검색 품질을 해친다. 섹션 구조가 아예 없다는 공통점이 있다.

```
bookindex.html (518 KB 색인)   index.html          sql-commands.html
reference-client.html          reference-server.html
biblio.html                    legalnotice.html
```

`<dl class="toc">` 도 파싱에서 제외한다. 이것은 정의 목록이 아니라 목차다. 실제로 조사
스크립트가 이를 정의목록으로 잘못 집계해 `runtime-config-connection.html` 의 첫 항목이
"19.3.1. Connection Settings 19.3.2. …" 로 나왔다. **같은 태그가 다른 의미로 쓰이며,
class 를 보지 않으면 조용히 틀린다.**

## 대안

### 고정 길이 슬라이딩 윈도우

기각. 구현은 가장 쉽지만 표와 코드 블록을 중간에서 자른다. 실측상 문서의 59.5%가 코드
블록을, 24.6%가 표를 포함하므로 피해가 국소적이지 않다.

### 재귀적 문자 분할 (LangChain `RecursiveCharacterTextSplitter` 류)

기각. 구분자 우선순위로 자르므로 순수 산문에는 무난하지만 HTML 구조를 모른다. 표 안의
`\n` 과 산문의 `\n` 을 구별하지 못한다. **우리는 구조를 이미 태그로 갖고 있는데 그것을
버리고 텍스트로 되돌린 뒤 추측하는 셈**이다.

### LLM 에게 청킹을 맡긴다

기각. 결정론적 계층과 LLM 계층의 경계를 무너뜨린다(BRIEF §4). 같은 입력에 다른 출력이
나오면 Phase 4~5 의 청킹 전략 비교 실험이 불가능해진다. 또한 1,148개 문서에 매번 비용이
든다.

### 문서 전체를 한 청크로 (청킹 없음)

기각. 크기 편차가 250배(2 KB ~ 518 KB)라 균일한 검색 단위가 되지 않는다.

## 결과

### 얻는 것

- 표·코드·정의 항목이 의미 단위로 보존된다
- 모든 청크가 섹션 앵커를 가져 근거를 절 단위로 링크할 수 있다
- 결정론적이라 청킹 전략 변경의 효과를 Phase 4~5 에서 측정 비교할 수 있다
- 임계값이 실측 분포에 근거하며 그 뜻을 문장으로 말할 수 있다

### 감수하는 것

- **PostgreSQL 문서의 DocBook HTML 구조에 결합된다.** 두 번째 소스(메일링 리스트)는
  구조가 전혀 다르므로 이 파서를 재사용할 수 없다. ADR 0002 대로 그때 인터페이스를
  고치며, **이 청킹 로직을 일반화하려 시도하지 않는다**
- 정의목록 항목 중 2.1%(108개)는 여전히 분할이 필요하다. 이 경우 항목 제목(`<dt>`)을
  각 조각에 반복 포함하지만, 완전한 해결은 아니다
- 표를 행 그룹으로 나누면 "표 전체를 봐야 답할 수 있는 질문"에는 약해진다.
  Phase 5 리랭킹에서 같은 표의 조각들을 함께 올리는 것으로 보완할 여지를 남긴다

### 구현 후 실측 (2026-09-10)

| 항목 | 값 |
|---|---|
| 문서 → 청크 | 1,131 → **16,442** |
| `chunk_id` 충돌 | 0 |
| 청크 길이 | median 214자, p90 1,008, p99 2,386, max 6,874 |
| 분할된 청크 | 352 (**2.1%**) — 분할은 예외에 머문다 |
| 임계값 초과 청크 | 149 — 전부 code(23)와 table(126), 자르지 않기로 한 것들 |
| 분할 표 조각의 헤더 보유 | 121/121 (**100%**) |
| 처리 시간 | 1.7초 |

**미해결로 남긴 것**: 50자 미만 청크가 13.95%(2,294개) 있다. `<pre>` 사이에 낀
`or` 같은 연결어가 독립 청크가 되기 때문이다. 검색 노이즈가 될 가능성이 높지만
**지금 고치지 않는다.** 평가셋 없이 청킹을 손대면 개선인지 노이즈인지 알 수 없다.
Phase 3 기준선 확보 후 측정과 함께 결정한다.

### 언제 재검토하는가

- **Phase 3 평가셋과 Phase 5 recall@k 측정 후.** 청킹은 감으로 고치지 않는다.
  기준선 없이 바꾸면 개선인지 노이즈인지 알 수 없다
- 임계값 세 개 중 어느 하나가 실측에서 **전부 걸리거나 하나도 걸리지 않을 때**
- 두 번째 소스를 넣을 때 — 재사용이 아니라 별도 구현이 원칙이다
