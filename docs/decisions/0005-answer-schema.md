# 0005. 답변 스키마와 근거 검증

- 상태: 채택됨
- 날짜: 2026-09-10

## 배경

이 프로젝트의 1번 절대 규칙은 "근거 없는 답변은 내지 않는다" 이다. 규칙을 문서에만
두면 지켜지지 않는다. 스키마와 검증으로 강제해야 한다.

그리고 이 구조는 나중에 바꾸기 어렵다. Phase 6 의 문장 단위 근거 추적과 프로젝트 2
(근거 일치 판정 모델)의 학습 데이터가 모두 이 모양을 전제한다.

## 결정

```
reasoning              : string            ← 맨 앞
causes[]               : description, evidence[], confidence
  evidence[]           : { chunk_id, quote }
checks[]               : string
insufficient_evidence  : bool
version_basis          : string            ← 코드가 채운다
```

### reasoning 을 맨 앞에 둔다

스키마가 답만 허용하면 모델이 즉시 결론을 내야 한다. 추론을 뒤에 두면 이미 답을 낸 뒤
이유를 짜맞추는 사후 합리화가 된다.

### 근거를 원인 후보마다 붙인다

답변 전체에 하나로 묶지 않는다. 어느 주장이 어느 문서에서 왔는지 구별할 수 없으면
근거 추적이 성립하지 않는다. Phase 6 과 프로젝트 2 가 (주장, 근거) 쌍을 전제한다.

### 근거는 `{chunk_id, quote}` 이며 **둘 다 검증한다**

- `chunk_id` — 실재하는가, **그리고 실제로 컨텍스트에 있었는가**
- `quote` — 그 청크 본문에 실제로 있는 문자열인가

`chunk_id` 만으로는 모델이 인용을 변형했는지 창작했는지 알 수 없다. `SourceRef` 전체를
모델이 생성하게 하면 URL 을 환각해도 검증할 방법이 없다 — 그래서 참조는 코드가
`chunk_id` 로부터 복원한다.

### 선택 필드를 두지 않는다

선택 필드 하나가 문법 상태 공간을 넓힌다. "없음"은 빈 배열로 충분히 표현된다.

### enum 값은 대소문자를 무시하고 해석한다

스키마에 enum 을 걸어도 지정하지 않은 표기가 돌아올 수 있다. `Confidence.parse` 가
소문자로 정규화하고, 알 수 없는 값은 `low` 로 떨어뜨린다.

### 걸러진 근거를 결과에 실어 보낸다

`DroppedEvidence(chunk_id, quote, reason)` 로 남긴다. 조용히 버리면 사용자는 답변이
온전히 검증된 것으로 읽는다.

### 근거 부족의 **책임 소재**를 구분한다

`insufficient_cause` 가 셋을 나눈다.

| 값 | 뜻 | 무엇을 고쳐야 하는가 |
|---|---|---|
| `model_declined` | 모델이 스스로 답하기를 거부 | 프롬프트 또는 컨텍스트 |
| `verification_removed_all` | 모델은 답했으나 검증이 전부 걸러냄 | 환각 — 모델 또는 검증 기준 |
| `no_causes_returned` | 거부도 환각도 아닌 빈 답 | 프롬프트 |

구분하지 않으면 "근거 부족" 한 덩어리만 보이고 무엇을 고쳐야 할지 알 수 없다.
실제로 이 구분이 없었을 때 정답 청크를 주고도 빈 답이 나오는 원인을 짚지 못했다.

### 인용 최소 길이 `MIN_QUOTE_CHARS = 20`

이보다 짧은 인용은 근거로 치지 않는다. `"the"` 같은 조각은 어느 청크에나 있어 우연히
일치하고, 그러면 quote 검증이 통과 도장으로 전락한다.

### 인용 비교는 공백 차이만 봐준다

정확 일치를 먼저 보고, 실패하면 공백만 정규화해 다시 본다. 개행을 공백으로 바꾸는 것은
인용의 변형이 아니지만 단어를 바꾸는 것은 변형이다.

## 대안

### `evidence: [SourceRef]` — 모델이 참조 전체를 생성

기각. 두 가지 문제가 있다. **모델이 URL 을 환각해도 검증할 수 없고**, 참조 JSON 이
청크당 median 222자여서 출력 토큰이 낭비된다. 참조는 우리가 이미 갖고 있다.

### `evidence: [chunk_id]` — 인용 없이 id 만

기각. 출력은 가장 작지만 **모델이 그 청크를 실제로 읽고 인용했는지 검증할 수 없다.**
Phase 6 과 프로젝트 2 가 (주장, 근거 문장) 쌍을 전제하므로 나중에 추가하면 재작업이다.
컨텍스트 비용 문제는 인용을 빼서가 아니라 **컨텍스트 표기를 줄여서** 푼다(Phase 7).

### 프롬프트로 "JSON 으로 답해라" 라고 부탁

기각. 프롬프트 지시는 확률을 기울일 뿐이고, 확률이 0 이 아니면 언젠가 뽑힌다. 파싱
실패가 언제 일어날지 예측할 수 없는 상태가 된다. `response_schema` 로 강제한다.

## 결과

### 얻는 것

- "근거 없는 답변은 내지 않는다"가 문서가 아니라 코드로 강제된다
- 근거를 하나도 살리지 못한 원인 후보는 애초에 결과에 오르지 않는다
- Phase 6 과 프로젝트 2 가 필요로 하는 (주장, 근거 문장) 쌍이 처음부터 쌓인다
- 실패의 책임 소재가 구분되어 무엇을 고쳐야 할지 알 수 있다

### 감수하는 것

- 인용을 함께 받으므로 출력 토큰이 늘어난다. 컨텍스트 비용은 Phase 7 에서 다룬다
- `MIN_QUOTE_CHARS = 20` 은 **측정 없이 정한 값**이다. 실제 인용은 79자였지만 표본이
  적다. Phase 3 에서 분포를 보고 조정한다
- 공백 정규화는 관대함의 정도를 정한 선택이다. 더 관대하면 변형을 놓치고, 더 엄격하면
  정직한 인용이 탈락한다

### 언제 재검토하는가

- **Phase 3 에서 인용 길이 분포와 탈락률을 측정한 뒤** — `MIN_QUOTE_CHARS` 와 공백
  정규화 수준을 함께 본다
- Phase 6 에서 문장 단위 추적을 구현할 때 — `quote` 가 문장 경계와 맞는지
- `verification_removed_all` 이 흔해지면 — 검증이 과하거나 모델이 환각한다
