# 0001. 프로젝트 범위와 1차 도메인 선택

- 상태: 채택됨
- 날짜: 2026-09-10

## 배경

인프라 운영 중 처음 보는 에러가 나면 검색 → 문서·이슈·스택오버플로 열람 → 유사 사례
탐색에 30분에서 몇 시간이 든다. 이를 줄이는 시스템을 만들되, **근거를 추적할 수 있어야**
한다는 제약을 둔다. 운영 중에는 틀린 조치의 대가가 크므로 출처 없는 답은 쓸 수 없다.

문제는 어느 도메인으로 첫 파이프라인을 검증하느냐다. 도메인을 잘못 고르면 파이프라인의
결함인지 데이터의 결함인지 구별할 수 없다.

## 결정

**1차 도메인을 PostgreSQL 18 로 한다.** 인덱싱 기준 버전은 **18.6** 이다.

**수집원은 공식 릴리스의 사전 빌드 HTML tarball 로 한다.**

```
https://ftp.postgresql.org/pub/source/v18.6/postgresql-18.6-docs.tar.gz
```

확장은 아래 순서로 하되 **한 번에 한 소스만** 추가한다. 여러 소스를 동시에 넣으면
무엇 때문에 문제가 생겼는지 구별할 수 없다.

| 단계 | 소스 | 새로 등장하는 문제 |
|---|---|---|
| 1 | PostgreSQL 공식 문서 | 기본 파이프라인 |
| 2 | 메일링 리스트 / 이슈 | 소스 추상화가 처음 시험됨 |
| 3 | Redis 또는 Nginx | 소스 간 라우팅 |
| 4 | Kubernetes | 검색 성능 |

## 대안

### 웹사이트 크롤링 (postgresql.org/docs/18/)

기각. **실측으로 tarball 이 우월함을 확인했다.** `errcodes-appendix.html` 을 양쪽에서
받아 비교한 결과:

| | tarball | 웹사이트 |
|---|---|---|
| `<table>` / `<tr>` / `<td>` | 3 / 310 / 577 | 3 / 310 / 577 |
| `<script>` | 0 | 2 |
| `<div>` | 8 | 34 |
| 크기 | 40 KB | 66 KB |

본문 콘텐츠는 완전히 동일하고 웹사이트 쪽에만 사이트 템플릿 크롬이 붙는다. 크롤링은
요청 예의·속도 제한·재현성 문제를 추가로 지며, 사이트가 바뀌면 과거 평가 결과와 비교가
깨진다. tarball 은 버전이 고정되고 오프라인 재현이 가능하다.

### 문서 원본 SGML (postgres 레포 `doc/src/sgml/*.sgml`)

기각. 의미 구조는 가장 정확하지만 DocBook SGML 파서를 직접 다뤄야 해 Phase 1 의 난이도가
불필요하게 올라간다. 빌드된 HTML 이 이미 의미 구조를 태그로 보존한다 —
`<table class="table">`, `<colgroup class="errorcode">`, `id="ERRCODES-APPENDIX"` 같은
앵커가 살아 있어 절 단위 근거 링크에 충분하다.
청킹이 HTML 구조만으로 부족하다고 **측정으로** 드러나면 그때 재검토한다.

### 공식 docs 페이지의 PDF

기각. `postgresql.org/docs/` 가 링크하는 유일한 다운로드 형식이지만, 표·코드 블록의
구조가 레이아웃에 녹아 복원이 어렵다. 청킹이 이 프로젝트의 첫 난제인데 가장 불리한
형식이다.

### 다른 1차 도메인 (Kubernetes, Nginx 등)

기각. PostgreSQL 은 문서가 체계적이고, 에러 코드가 SQLSTATE 로 표준화되어 있으며,
버전별 문서가 명확히 분리되어 있다. 첫 파이프라인을 검증하기 가장 쉽다. Kubernetes 는
규모가 커서 검색 성능 문제가 파이프라인 결함과 섞인다.

## 결과

### 얻는 것

- 버전이 고정된 재현 가능한 코퍼스. Phase 3 평가셋의 기준이 흔들리지 않는다
- 사이트 크롬 없는 깨끗한 XHTML. well-formed XML 로 엄격 파싱 가능
- 의미 있는 앵커(`id="ERRCODES-APPENDIX"`)로 절 단위 근거 링크 가능
- SQLSTATE 표준 코드로 정확 매칭 검색의 앵커 확보

### 감수하는 것

- **문서 갱신을 자동으로 따라가지 않는다.** 새 마이너 릴리스마다 tarball 을 다시 받아야
  한다. 대신 언제 무엇을 인덱싱했는지가 명확해진다
- **수집원이 공식 docs 페이지에 링크되지 않은 경로다.** 릴리스 디렉터리 구조가 바뀌면
  수집이 깨진다. 수집 단계에 URL 존재 확인과 sha256 검증을 넣는다
- 공식 문서만으로는 "실무에서 실제로 이 에러가 났을 때" 사례가 부족하다. 확장 2단계
  (메일링 리스트)가 이를 메운다

### 언제 재검토하는가

- **PostgreSQL 19 정식 릴리스 시점.** 다중 버전 인덱싱이 처음으로 실제 문제가 된다.
  현재 19 는 Beta 3 이다
- Phase 3 평가에서 공식 문서만으로 답할 수 없는 질문이 30개 중 상당수로 드러날 때 —
  확장 2단계를 앞당긴다
- HTML 청킹으로 표 구조 보존이 불가능하다고 측정될 때 — SGML 원본을 재검토한다
