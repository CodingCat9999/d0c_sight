# 0009. 평가 실행 — 폴백 차단, 레이트 리밋, 불완전 표시

- 상태: 채택됨
- 날짜: 2026-09-11
- 관련: ADR 0006 을 일부 대체한다 (아래 "429 대응" 절)

## 배경

무료 티어에서 30문항을 반복 실행해야 한다. 세 가지가 측정을 망칠 수 있다 —
모델이 중간에 바뀌는 것, 레이트 리밋으로 일부 문항이 빠지는 것, 그리고 빠진 것을
모른 채 집계하는 것.

## 결정

### 1. 평가 실행에서 모델 폴백을 끈다

`run_case` 가 `fallback_models=()` 로 설정을 덮어쓴다. 503 은 폴백이 아니라 **같은
모델 재실행**으로 다루고, 재실행 횟수를 결과에 기록한다.

다른 모델의 답을 같은 기준으로 비교하면 측정이 무의미해진다. 평가 밖(일반 `diagnose`)
에서는 폴백이 그대로 살아 있다 — 거기서는 가용성이 정확성보다 중요하다.

### 2. 불완전한 실행에서는 통과율을 계산하지 않는다

실패 문항이 하나라도 있으면 `complete = False` 이고 `pass_rate` 는 **`None`** 이다.

30문항 중 3개가 실패했는데 27개만 보고 "87% 통과" 라고 하면 틀린 숫자다. 경고를
띄우는 것으로는 부족하다 — 숫자가 있으면 사람은 그것을 읽는다. **계산 자체를 막았다.**

### 3. 429 대응 — 실측한 뒤에 만들었다

ADR 0006 은 "429 를 실제로 관측했을 때 `retry-after` 존중이 필요한지 판단한다" 로
남겨두었다. **Phase 3 에서 관측했으므로 여기서 결정한다.**

실측: 20문항을 48초에 28회 호출했더니 `429 RESOURCE_EXHAUSTED` 로 4문항이 실패했다.
SDK 기본 재시도(5회, 1s→2s→4s→8s)와 우리 재실행(3회)이 **모두 같은 레이트 리밋
윈도우 안에서 소진됐다.** 백오프 총합이 15초 남짓인데 윈도우는 60초다.

**백오프를 늘리는 대신 애초에 한도를 넘지 않게 한다.**

```
MIN_CALL_INTERVAL_S = 4.0      # 60초 / 분당 15회 = 4초
```

뜻: *"무료 티어 Lite 한도가 분당 15회이므로 호출 사이를 4초 이상 벌린다."*
캐시 적중에는 기다리지 않는다 — 기다릴 이유가 없다.

`retry-after` 존중은 **여전히 만들지 않는다.** 간격을 두면 429 자체가 발생하지 않고,
발생하지 않는 경우를 방어하는 코드가 되기 때문이다.

### 4. 캐시 키에 프롬프트 버전과 모델을 넣는다

```
sha256(case_id + question + gold + model + prompt_version + settings)
```

빠지면 다른 프롬프트의 결과가 재사용되어 **무엇을 쟀는지 모르는 숫자**가 남는다.
`PROMPT_VERSION` 을 `llm/prompt.py` 상수로 두어 프롬프트를 고칠 때 함께 올리게 했다.

### 5. 결과를 항목별로 저장한다

총점만 보면 87 → 91 일 때 새로 실패한 2개를 놓친다. 실행마다 평가셋 버전, 모델,
프롬프트 버전, 모든 파라미터, 완전성, 문항별·항목별 결과를 남긴다.

## 대안

### 폴백을 켠 채로 실행하고 사후에 걸러낸다

기각. `attempted_models` 로 식별은 가능하지만, 일부 문항만 다른 모델이 답한 실행은
**어느 쪽으로도 해석할 수 없다.** 애초에 발생시키지 않는 편이 낫다.

### 실패 문항을 빼고 통과율을 낸다

기각. 실패가 특정 유형에 몰려 있으면(실제로 `no_answer` 2개가 함께 실패했다) 남은
문항의 통과율은 체계적으로 낙관적이다.

### SDK 백오프를 늘린다

기각. 재시도 횟수를 늘리면 같은 윈도우에서 더 많이 실패하고, 대기만 길어진다.
레이트 리밋은 재시도 문제가 아니라 **호출 속도** 문제다.

### 캐시 없이 매번 실행

기각. 무료 티어 하루 500회로는 개선 반복이 불가능하다. 실제로 프롬프트를 고치지 않은
재실행이 API 호출 0회로 끝났다.

## 결과

### 얻는 것

- 한 실행 안에서 모델이 고정되어 결과를 비교할 수 있다
- 레이트 리밋으로 조용히 빠진 문항이 통과율에 섞이지 않는다
- 캐시 덕에 프롬프트·설정이 같으면 재실행이 무료다

### 감수하는 것

- **4초 간격 때문에 30문항에 최소 2분이 든다.** 캐시 미적중 시에만 해당한다
- `MIN_CALL_INTERVAL_S` 는 Lite 한도(분당 15) 기준이다. **Flash 계열(분당 5)로 돌리면
  부족하다** — 그때는 12초로 올려야 하며, 현재 코드는 자동으로 맞추지 않는다
- 캐시가 오래되면 코퍼스가 바뀌어도 재사용된다. 캐시 키에 코퍼스 버전이 없다 —
  평가셋 무결성 검사가 이를 잡지만 두 장치가 분리되어 있다

### 언제 재검토하는가

- **Flash 계열로 평가를 돌릴 때** — 간격을 분당 5회 기준으로 바꿔야 한다
- 4초 간격에도 429 가 나면 — 한도가 바뀌었거나 계정이 다른 등급이다
- 캐시 재사용이 잘못된 결과를 준 사례가 나오면 — 키에 코퍼스 버전을 넣는다
