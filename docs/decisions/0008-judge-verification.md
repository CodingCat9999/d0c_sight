# 0008. judge 를 믿기 전에 검증한다

- 상태: 제안됨 (일치율 측정 대기)
- 날짜: 2026-09-11

## 배경

기계로 채점할 수 없는 것이 둘 남는다 — 근거 일치와 완전성. 여기에 LLM judge 를 쓴다.

문제는 **judge 가 무엇을 재는지 모른다는 것**이다. 검증 없이 쓰면 숫자는 늘어나는데
그 숫자가 무엇을 뜻하는지 알 수 없다.

## 결정

### judge 설계

- **점수가 아니라 판정.** `verdict` 는 boolean 이며 스키마에 척도가 없다
- **reasoning 을 먼저 쓰게 한다.** 판정을 먼저 내면 이유를 짜맞추게 된다
- **생성 모델과 다른 모델을 쓴다.** 자기가 쓴 답을 자기가 채점하면 선호 편향이 든다.
  생성 `gemini-3.1-flash-lite` / judge `gemini-3.5-flash-lite`
- **외부 지식 사용을 금지한다.** 사실이지만 근거로 뒷받침되지 않는 답은 `no` 다.
  이것을 명시하지 않으면 judge 가 자기 PostgreSQL 지식으로 채점한다
- **항목을 한 요청에 묶는다.** 항목마다 호출하면 무료 티어 한도를 넘는다

### 검증 절차 — 이 순서를 건너뛰지 않는다

```
1. 사람이 30문항을 직접 채점한다 (예/아니오)
2. judge 에게 같은 30문항을 채점시킨다
3. 일치율을 측정하고 기록한다
4. 낮으면 judge 프롬프트를 고친다 — 어긋난 케이스가 무엇을 오해하는지 보여준다
5. 충분히 일치할 때만 judge 를 쓴다
```

**사람 채점은 사용자가 한다.** 대신할 수 없다 — 대신하면 "LLM 이 만든 정답으로 LLM 을
채점"하는 순환이 되고, 일치율은 두 LLM 이 같은 편향을 공유하는지만 재게 된다.

### 일치율 임계값은 아직 정하지 않았다

**실측 분포를 보고 정한다.** 전부 통과하는 값도 아무도 통과 못 하는 값도 잡음이다.
값을 정할 때 그 뜻을 한 문장으로 적는다.

임계값을 미리 적어두면 측정 결과를 그 숫자에 맞춰 해석하게 된다. 그래서 이 ADR 은
**"제안됨"** 상태이며, 일치율을 측정한 뒤 임계값과 함께 "채택됨" 으로 바꾼다.

### `no_missing_exception` 은 애매할 가능성이 높다 — 미리 적어둔다

"중요한 예외를 빠뜨렸는가" 에서 **"중요한" 의 기준이 사람마다 다르다.** 일치율이
낮게 나온다면 judge 가 틀린 것이 아니라 항목이 애매한 것일 수 있다.

그 경우 쪼갠다.

```
현재   : 근거에 있는 중요한 예외를 빠뜨리지 않았는가
쪼개면 : (1) 근거에 "다만/단/제외" 같은 단서가 있는가
         (2) 있다면 답변이 그것을 언급했는가
```

후자가 훨씬 재현 가능하다. **지금 쪼개지 않는다** — 애매하다는 것이 측정되기 전에
고치면 무엇을 고친 것인지 알 수 없다. 일치율을 보고 판단한다.

### `no_missing_exception` 채점 기준 — "중요한" 을 우회한다

주관적 판단을 피하기 위해 단서의 **존재 여부**를 먼저 본다.

```
1. 근거 청크에 "다만 / 단 / 제외 / ~인 경우는" 같은 단서가 명시적으로 있는가
     없으면  → 해당 없음 (빠뜨릴 예외가 없다)
     있으면  → 2 로
2. 답변이 그 단서를 언급했는가 → 예/아니오
```

이렇게 하면 "중요한" 이라는 척도 없는 판단을 우회한다. 그래도 애매하면 **그 애매함
자체를 메모에 남긴다** — judge 가 틀린 경우와 항목이 애매한 경우를 구별하는 근거다.

### 어긋난 케이스를 따로 기록한다

사람도 애매하다고 느낀 항목일 가능성이 크다. 그러면 judge 가 아니라 **항목 자체를**
고쳐야 한다.

## 대안

### judge 없이 기계 채점만

기각. 근거 일치와 완전성은 코드로 판정할 수 없다. 다만 judge 결과를 기계 채점과
**섞어서 하나의 점수로 만들지 않는다** — 신뢰도가 다르다.

### 생성과 같은 모델로 채점

기각. 자기 선호 편향. 같은 모델이 같은 실수를 정상으로 판정한다.

### 일치율 측정 없이 judge 사용

기각. 이 프로젝트가 하지 않기로 한 것의 전형이다 — 검증되지 않은 측정을 근거로 쓰는 것.

## 결과

### 얻는 것

- judge 가 무엇을 재는지 아는 상태에서 쓴다
- 어긋난 케이스가 평가 항목의 결함을 드러낸다

### 감수하는 것

- **사람 채점에 사용자의 시간이 든다.** 30문항 × 2항목이며, 이것 없이는 judge 를 쓸 수 없다
- 일치율이 낮으면 judge 프롬프트를 고치고 다시 채점해야 한다
- judge 프롬프트를 고치면 과거 일치율은 무효다. 그래서 `JUDGE_PROMPT_VERSION` 을
  일치율 결과에 함께 기록한다

### 언제 재검토하는가

- **일치율을 처음 측정한 직후** — 임계값을 정하고 이 ADR 을 "채택됨" 으로 바꾼다
- judge 프롬프트를 고칠 때마다 — 일치율을 다시 잰다
- 생성 모델을 바꿀 때 — judge 모델이 여전히 다른지 확인한다
