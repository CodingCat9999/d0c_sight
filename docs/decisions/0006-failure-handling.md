# 0006. 실패 대응 — 재시도를 만들지 않고 관측한다

- 상태: 채택됨
- 날짜: 2026-09-10

## 배경

무료 티어에는 분당 요청 제한이 있고, 실측해보니 503(high demand)도 일상적으로
발생한다. 재시도가 필요해 보인다.

그런데 **실측 없이 만든 정책은 안 걸리는 경우를 방어하고 걸리는 경우를 놓친다.**
먼저 SDK 가 이미 무엇을 하는지 확인해야 한다.

## 결정

### 1. SDK 기본 재시도를 그대로 쓴다. 중복 구현하지 않는다

`google-genai` 소스를 직접 확인한 값이다.

```
_RETRY_ATTEMPTS      = 5       (초기 호출 포함)
_RETRY_INITIAL_DELAY = 1.0s
_RETRY_EXP_BASE      = 2
_RETRY_MAX_DELAY     = 60.0s
_RETRY_JITTER        = 1
대상 상태코드         = 408, 429, 500, 502, 503, 504
```

**429 가 이미 포함되어 있다.** 무료 티어의 분당 제한은 SDK 가 지수 백오프로 처리한다.
그 위에 우리 백오프를 얹으면 대기 시간이 곱해지기만 한다.

### 2. 그 위에 얹는 것은 모델 폴백 하나뿐이다

SDK 가 5회를 다 쓰고도 실패하면 다음 후보 모델로 넘어간다. 설정에 후보 목록을 두고
순차 시도한다.

```
gemini-3.7-flash → gemini-3.5-flash → gemini-3.6-flash → gemini-3.1-flash-lite
```

**이것은 가용성 기반 폴백이며 품질 기반 라우팅이 아니다.** 후보 순서는 "더 나은 답을
주는 순서"가 아니라 "살아 있을 가능성이 높은 순서"다. 품질 기반 라우팅은 Phase 3
평가셋이 생긴 뒤 Phase 9 에서 다룬다. 이 둘을 섞으면 "왜 이 모델이 답했는가"에 두 가지
이유가 생겨 결과 해석이 불가능해진다.

### 3. 결과에 무엇이 답했는지 기록한다

`GenerationRecord.attempted_models` 가 시도 순서 전체를, `model` 이 성공한 모델을,
`fallback_count` 가 폴백 횟수를 남긴다. 폴백이 일어날 때마다 `WARNING` 을 남긴다.
가용성 문제가 조용히 묻히면 "왜 답이 달라졌는가"를 설명할 수 없다.

### 4. 이 Phase 에서 하는 일은 관측이다

- `stop_reason` 을 반드시 기록한다
- 토큰(입력/출력/thinking)과 지연을 기록한다
- 파싱 실패 시 실패 유형과 `stop_reason` 을 함께 남긴다

**실패 유형이 실측된 뒤에 대응을 설계한다.**

### 5. 로그와 예외에 원문과 비밀값을 싣지 않는다

- API 키는 `scrub()` 로 지운다. SDK 예외를 그대로 흘리지 않고 `ProviderError` 로
  감싸며, **`from None` 으로 예외 체인을 끊는다** — 체인을 남기면 원본 예외에 담긴
  키가 스택 트레이스에 그대로 나온다
- 파싱 실패 예외에 응답 본문을 넣지 않는다. `stop_reason` / 길이 / 실패 위치만으로
  진단에 충분하다
- 프롬프트 원문을 로그에 남기지 않는다

이 가드들에는 짝 테스트가 있고, 무력화했을 때 실패하는 것을 확인했다.

## 대안

### 직접 지수 백오프를 구현한다

기각. SDK 가 이미 한다. 중복 구현하면 대기 시간이 곱해지고, 두 층 중 어디서 몇 번
재시도했는지 알 수 없어진다.

### `retry-after` 헤더를 직접 존중하는 재시도를 만든다

**지금은 기각, 조건부 보류.** 실측에서 429 를 아직 한 번도 만나지 못했다(마주친 것은
503 뿐이다). 걸리지 않는 경우를 방어하는 코드가 된다. **429 가 실제로 관측되고 SDK 의
지수 백오프가 `retry-after` 보다 짧게 기다리는 것이 확인되면** 그때 만든다.

### 폴백 없이 실패시킨다

기각. 실측에서 `gemini-3.7-flash` 가 SDK 재시도 5회를 모두 쓰고도 503 으로 죽는 일이
반복됐다. 폴백을 넣은 뒤 같은 상황에서 `gemini-3.5-flash` 로 넘어가 정상 응답을 받았다.

### 폴백 후보를 품질 순으로 정렬한다

기각. 품질 순서를 정할 근거가 없다(평가셋 없음). 근거 없이 정한 순서가 "품질 순"이라는
이름을 달면, 나중에 그것이 측정된 사실처럼 굳는다.

## 결과

### 얻는 것

- 무료 티어의 503 이 작업을 멈추지 않는다 (실측으로 확인)
- 어떤 실패가 실제로 일어나는지 데이터가 쌓인다
- 키와 원문이 로그에 새지 않는다 (변이 검증으로 확인)

### 감수하는 것

- **폴백이 일어나면 답변이 다른 모델에서 나온다.** 같은 질문에 다른 답이 나올 수 있고,
  이는 Phase 3 평가의 잡음이 된다. `attempted_models` 기록으로 사후 식별은 가능하지만,
  평가 실행 중 폴백이 발생하면 그 결과를 그대로 비교해서는 안 된다
- 후보 모델 4개를 모두 소진하면 실패한다. 재시도 총 20회(4 × 5)에 최대 대기가 길다
- `retry-after` 를 존중하지 않는다. 429 가 관측되면 재검토한다

### 언제 재검토하는가

- **429 를 실제로 관측했을 때** — `retry-after` 존중이 필요한지 판단한다
- Phase 3 평가 중 폴백이 자주 발생하면 — 평가 실행은 단일 모델 고정으로 바꾼다
- Phase 9 에서 품질 기반 라우팅을 도입할 때 — 이 ADR 을 대체하는 새 ADR 을 쓴다
