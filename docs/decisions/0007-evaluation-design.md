# 0007. 평가 설계 — 판정, 다양성, 홀드아웃

- 상태: 채택됨
- 날짜: 2026-09-11

## 배경

여기서 만든 기준선이 Phase 4~9 전체의 판단 근거가 된다. 기준선이 흔들리면 이후의
모든 개선이 감으로 이루어진다.

## 결정

### 1. 점수가 아니라 판정이다

모든 채점 항목은 예/아니오다. `1~5` 같은 척도를 쓰지 않는다.

**척도는 재현되지 않는다.** 두 사람이 독립적으로 매기면 다른 값이 나오고, 그러면
87 → 91 이 개선인지 잡음인지 구별할 수 없다. 판정 항목은 셋을 만족해야 한다 —
확인 가능한가, 두 사람이 같은 답을 내는가, 애매하지 않은가. 애매하면 항목이 잘못
쓰인 것이므로 더 쪼개거나 버린다.

### 2. 기계 채점을 먼저 다 짠다

코드 채점은 공짜고 완벽히 재현되며 CI 에서 매번 돌 수 있다. 여섯 항목을 기계가 맡는다.

```
schema_valid · cited_ids_exist · quotes_verified
gold_cited · version_matches · no_answer_declined
```

judge 는 판단이 필요한 둘에만 쓴다 — 근거 일치, 완전성.

### 3. 케이스 선정은 다양성 기준이다

대표성으로 고르지 않는다. 가장 크고 대표적인 데이터가 버그를 숨긴다.

| 축 | 분포 |
|---|---|
| 유형 | error 11 / config 9 / concept 6 / **no_answer 4** |
| 검색 축 | semantic_only 9 / both 7 / keyword_only 7 / multi_chunk 7 |
| 출처 | mailing_list 15 / documentation 15 |
| 함정 | similar_parameter 5 / exception_clause 4 / version_dependent 2 |

**문서 유래를 절반으로 제한한다.** 공식 문서에서 기계적으로 뽑은 문항이 많아지면
문서를 문서로 검증하는 셈이 되어 평가셋이 쉬워진다. 나머지 절반은 실제
pgsql-general 스레드에서 왔고 각 문항에 URL 이 있다.

**`no_answer` 문항은 문서에 정말 없는지 코퍼스로 확인한다.** 실제로 `pgbouncer`(1건)와
`mysql`(3건)은 문서에 있어서 후보에서 뺐다. "없다고 생각했는데 있었다" 면 그 문항은
정반대를 검증하게 된다.

### 4. 홀드아웃을 분리한다

개선용 20 / 홀드아웃 10. 홀드아웃은 손대지 않다가 중요한 결정 시점에만 확인한다.
30문항 전부로 계속 튜닝하면 그 30개만 잘하는 시스템이 된다.

### 5. 검색 평가와 생성 평가를 분리한다

생성 평가는 **정답 청크를 직접 주입해서** 돌린다. 검색 변수가 제거되고 생성 능력만
측정된다. 답이 틀렸을 때 검색이 못 찾은 건지 모델이 잘못 읽은 건지 구별할 수 없으면
고칠 수가 없다.

### 6. `k = 5`

프롬프트에 실제로 넣을 청크 개수다. 100개를 찾아도 5개만 쓰면 recall@100 은 의미가
없다. `k` 를 결과에 함께 기록해 값을 바꿔도 과거와 비교할 수 있게 한다. 지금은
계산기만 만들었고 기준선은 검색이 붙는 Phase 4 에서 잰다.

### 7. 기준선은 `temperature = 0` 실행만이다

지정하지 않으면 공급사 기본값이 쓰이고 그것은 비결정적이다. 실제로 같은 20문항을
같은 모델·프롬프트로 두 번 돌렸더니 **90% 와 75%** 가 나왔다.

```
90%  — 비결정적 실행의 한 표본. 기준선이 아니다
75%  — temperature 0 고정, 101개 항목 전부 재현 확인. 첫 기준선
```

떨어진 것이 아니라 **처음으로 제대로 잰 숫자**다. 이 구별을 기록해두지 않으면
나중에 "왜 떨어졌지" 로 헷갈린다.

`temperature = 0` 도 완전한 결정론은 아니다 — 부동소수점 연산 순서 때문에 드물게
어긋날 수 있다. 그런 경우가 나오면 버그가 아니라 정상이다.

### 8. 형식 실패와 내용 실패를 따로 센다

기준선의 실패를 분류해보니 이렇다.

| 성격 | 건수 | 뜻 |
|---|---|---|
| **형식** (인용문은 코퍼스에 실재, 내용은 맞음) | 9건 (**82%**) | `chunk_id` 축약, 긴 인용의 변형 |
| **내용** (정답을 못 찾거나 일부만 인용) | 2건 (18%) | `all_gold_cited` 실패 |

**형식 실패를 전부 고치면 89% → 98% 가 되지만, 답변이 실제로 좋아진 부분은 0 이다.**
사용자 입장에서는 원래도 맞는 답이었다.

```
형식 실패 개선  →  검증 파이프라인이 정확해진다
내용 실패 개선  →  답변이 실제로 좋아진다
```

둘 다 필요하지만 의미가 다르다. **총점 하나로 뭉치면 이 구분이 사라지고, "인용 형식
준수율" 을 "답변 품질" 로 착각하게 된다.** §10 의 개선을 평가할 때 반드시 나눠 센다.

### 9. 항목이 서로 독립적이지 않다 — 알려진 한계

형식 실패 하나가 `cited_ids_exist` · `quotes_verified` · `gold_cited` 를 **동시에**
실패시킨다. 근거가 검증에서 탈락하면 셋 다 무너지기 때문이다. 따라서 총점은 하나의
원인을 최대 3배로 센다.

지금 고치지 않는다. 항목을 합치면 "무엇이 틀렸는가" 를 잃고, 가중치를 주면 그 가중치의
근거가 없다. **대신 문항 단위 통과율(`pass_rate`)과 항목별 집계를 함께 본다** — 문항
단위로 보면 한 원인이 한 번만 세어진다.

## 대안

### 5점 척도 + 평균

기각. 재현되지 않는다. 그리고 평균은 어느 항목이 뒤집혔는지 감춘다.

### judge 에게 전부 맡긴다

기각. 기계로 되는 것까지 judge 에 맡기면 비용이 들고, 재현되지 않으며, 무료 티어
한도에 걸린다. 그리고 judge 가 틀렸는지 확인할 방법이 없다.

### 문항을 전부 공식 문서에서 뽑는다

기각. 쉽고 빠르지만 평가셋이 문서 구조를 그대로 따라가 실제 질문 분포와 멀어진다.

### 홀드아웃 없이 30문항 전부로 튜닝

기각. 과적합을 감지할 방법이 사라진다.

## 결과

### 얻는 것

- 개선을 숫자로 판단할 수 있다. 항목별로 저장하므로 어느 항목이 뒤집혔는지 보인다
- 기계 채점이 CI 에서 매번 돌 수 있다
- 평가셋 자체가 포트폴리오 산출물이 된다

### 감수하는 것

- **문항 30개는 적다.** 통계적으로 유의미한 차이를 재기엔 부족하고, 한 문항이 3.3% 다.
  작은 차이를 유의미하다고 읽지 않도록 주의해야 한다
- 정답 청크 라벨은 사람의 판단이며 틀릴 수 있다. 무결성 검사는 라벨이 **썩는 것**을
  막을 뿐 처음부터 틀린 라벨은 잡지 못한다
- 생성 평가가 정답 청크를 주입하므로 **검색이 붙은 뒤의 실제 성능보다 낙관적**이다

### 언제 재검토하는가

- 문항 하나가 결과를 좌우하는 일이 반복될 때 — 문항 수를 늘린다
- 홀드아웃과 개선용의 성적이 크게 벌어질 때 — 과적합이다
- 어느 판정 항목이 늘 100% 이거나 늘 0% 일 때 — 그 항목은 아무것도 재고 있지 않다
